# 50 ms 悬浮时钟优化实测

日期：2026-10-27。结论：**已消除原有 100 ms 绘制缓存，但严格“每个样本不超过 50 ms”未达标。** 仅模拟器，没有真机数据。

## 修改

- 数字在实际 onDraw 时重新取时间，复用原有绝对锚点算法；不会把服务检查时的旧数字留到下一帧。
- 最小重绘请求间隔 16 ms，按系统帧边界绘制，避免无间隔逐帧请求压满软件渲染器。只在浮窗可见且附着时续约。
- 面板使用不透明纯色底，移除重复背景填充。准星仍透明；没有新增生产依赖、网络线程或提高生产周期同步频率。
- 任务截止仍是独立调度，既有参考锁定、显式启停、取消、不重放保持。

## 外部对照

四个方案均使用 R8 优化包、同一 API 37 SwiftShader 模拟器，主页后台、京东来源每 60 秒同步。每轮 180 秒，独立进程每秒另取一次京东响应并读取绘制字符，共各 181 个有效样本；外部请求失败均为 0。主机负载和网络并非受控恒定，不把不同时间窗口当作严格实验室 A/B；每组原始数据均保留。

单位：毫秒。p95 为排序向上取整位置。

| 方案 | 显示绝对估算偏差 p50 / p95 / 最大 | >50 ms 数量 | 单核 CPU 区间中位 |
| --- | --- | ---: | ---: |
| 直接每帧续约 | 27 / 62 / 125 | 23/181 | 55.48% |
| 限制重绘请求间隔 | 17 / 60 / 185 | 15/181 | 22.02% |
| 限制间隔＋不透明面板 | 21 / 51 / 100 | 10/181 | 21.83% |
| 再加单回调去重（最终版本） | 29 / 145 / 297 | 49/181 | 23.54% |

不透明面板第一轮的字符相对最新应用参考的滞后为 p50 11 ms、p95 47 ms、最大 104 ms。进程 PSS 23030～25740 KiB，约 22.5～25.1 MiB。

该轮估算偏差 <=50 ms 的比例为 171/181（约 94.5%），**不能写成 100% 达标，也没有达到 95% 样本均小于等于 50 ms**。外部请求 RTT 中位 100 ms、最大 123 ms，单独对照的半 RTT 不确定度中位就有 50 ms。按上述 RTT 假设区间，13 个样本可判在限内，168 个无法确认，0 个可排除网络不确定度后判定超限；这些无法确认的样本全部保留，不能改判为通过。

最终单回调版本 49/181 超限，不能用前一轮较好数据替代。相对应用参考的字符滞后 p50 16 / p95 50 / 最大 128 ms；外部请求 RTT 中位 133 / 最大 716 ms，应用来源请求最大 432 ms，参考对外部估计本身范围 -291～293 ms。按 RTT 区间，51 个限内、103 个无法确认、27 个可判超限。同步参考若在观察前后切换，字符与参考差也可能暂时为负；不是人为提前时钟。最终 PSS 23075～25850 KiB（约 22.5～25.2 MiB）；仅 6 个资源样本，CPU 是约 30 秒区间值，不是瞬时峰值、手机功耗或无限运行证明。单回调改动用于防止请求链累积，当前不同网络窗口的结果并不证明它降低了绝对偏差。

图形诊断在该轮运行中记录帧 p95 34 ms、p99 65 ms，存在慢绘制命令与主线程延迟。该诊断包含启动阶段，不能把所有慢帧都算作稳定状态；独立样本中观察到的长画面年龄也不能由校时公式修复。

## 功能与采样校正

TDD 初始在旧版观察到相对参考最大 124 ms 滞后，明确失败。切换绘制时取时后，早期采样器仍在 UI 线程遍历窗口并创建解析器，记录过 83 ms 峰值。随后将采样时间放到读取瞬间，解析移至测试线程并缓存对象：120 个单独采样的 p50 14 ms、p95 24 ms、最大 33 ms。该短测不是外部 50 ms 已达标的证据；上述 R8 全量外部对照仍保持失败。

功能回归另用确定性测试验证：主线程停顿后直接触发一次测试绘制，输出时间必须落在该次绘制调用的前后参考时刻之间，不能等待旧服务 tick 才更新。此主动绘制只存在于功能测试，不用于外部性能采样。完整运行同时记录普通采样的全部年龄及是否 <=50 ms，不靠放宽性能门槛来通过功能回归。

功能回归曾在停止按钮操作后立即检查状态而失败；触摸递交及浮窗监听器的 post 回调均异步完成，测试改为有界等待任务停止且图标复位，不修改产品停止行为。失败记录保留，不把它作为 50 ms 性能结果。

扩展点击验收发现一次派发晚 5 ms 且系统报告完成，但目标没有触摸事件。将准星输入准备从提前 100 ms、至少等待 50 ms 调整为提前 250 ms、至少等待 150 ms，保持绝对截止时派发和不补点。之后一轮 100/100 次均由独立目标实际接收，无提前样本；DOWN 延迟 p50 14 / p95 89 / 最大 304 ms，onClick 延迟 p50 52.5 / p95 134 / 最大 623 ms，仍不满足每次 50 ms 的点击要求。这轮数据在最后的单回调去重改动之前采集，作为输入准备调整证据，不冒充最终版本性能。

最终单回调版本另测 30 次，30/30 均实际接收，无提前样本：派发延迟 p50 5 / p95 42 / 最大 60 ms，DOWN 延迟 p50 8 / p95 60 / 最大 69 ms，onClick 延迟 p50 43.5 / p95 88 / 最大 112 ms。同样不满足每次 <=50 ms。CPU 区间中位 42.31%，PSS 23680～25197 KiB；仅 3 个资源样本，反复创建/启停窗口的活跃负载不能与静态时钟直接比较。

最终版本完整 32 项功能回归通过。普通字符采样 120 个，相对应用参考的年龄 p50 1 / p95 12 / 最大 38 ms；仍不替代外部对照。标准检查首次因仅代码创建的私有 ClockFace 缺少 XML 构造器而被 Lint 拒绝，随后为必须注入所选时钟的此类明确标注 ViewConstructor 例外，不引入会退回本机时间的备用构造器；该注解不改变运行逻辑。

最终 59 个单测零失败，标准 Lint、Debug、R8 Release、可选 benchmark 构建/Lint 及独立目标 Lint 均通过。已恢复普通 Debug、原配置并移除两个测试组件，没有重启模拟器或修改 IDEA 内嵌设备设置。普通 Debug/Release Manifest 不含 benchmark Provider。全部四轮时钟、五轮点击（包括失败）、TDD 和功能原始结果、APK 指纹与资源采样保存至 [验收证据](acceptance/2026-10-27-clock-50ms.json)。

## 能保证到哪里

50 ms 是合理的优化/验收目标，但当前证据不支持任意网络、系统负载下每次达标。公网响应的未知单向延迟、未承诺精度的京东请求 ID，以及系统停止绘制，都有可能超过预算。增加同步频率或加大时钟数字刷新率不能消除这些误差。

本次没有人为提前时钟、提前点击、自动更换来源、过滤超标样本或将中位数包装成最大值。若需求是一次超限也不能接受，当前 Android 悬浮时钟＋该公网接口的方案不能按这一硬指标验收，需要重新约定可信授时/执行环境与无法确认精度时的行为。

## 复现

先开模拟器无障碍，使用 JDK 17 和 D/E 盘 Gradle 缓存：

```powershell
.\scripts\acceptance.ps1
.\scripts\timing-acceptance.ps1 -ClockDurationMillis 180000 -ClockSampleMillis 1000 -ClockErrorLimitMillis 50 -Label clock-50ms-verify
python tools/timing-report.py .tools/timing/clock-50ms-verify
```

严格超限时脚本按预期失败并恢复普通 Debug，result.json 仍完整保存。不要反复重跑挑一轮成功来代替保留失败。
