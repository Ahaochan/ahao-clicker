# 0.2.0 性能优化记录

最新定时准时性优化、同条件 R8 延迟分布与长期校时验证见 [TIMING_RESULTS.md](TIMING_RESULTS.md)；下方保留 2026-10-25 真机的历史 CPU/PSS 测量。

日期：2026-10-25。设备：Xiaomi 25060RK16C，Android 16 / HyperOS 3，1280×2772、520 dpi。

2026-10-26 更新：以下是旧版界面的历史测量。当前首页已移除连点/多点表单，新多点录制浮窗暂未开放；旧 ReleaseAcceptance 依赖该表单，暂时不能重现。scripts/release-acceptance.ps1 会在任何设备操作前明确退出，待新功能及验收驱动适配后恢复。当前定时浮窗功能由 acceptance.ps1 验证，本次未重测优化包的真机 CPU、PSS 或点击性能。

## 本轮目标

降低独立悬浮时钟的持续 CPU 开销；本机目标为常态单核 CPU 不高于 10%、相对重测基线至少降低 50%，PSS 不明显回退（5 MiB 以内）。保留 HH:mm:ss:SSS、触发前的细致显示、停止路径和单次点击语义，不增加生产依赖。

## 定位与修改

优化前重新测得时钟约占单核 CPU 17.705%；线程短测中 RenderThread 约 10.20%、应用主线程约 6.04%。此前设备检查已确认硬件加速启用。主要可减少的工作是持续数字重绘，以及首页周期性重设相同文本导致的绘制；未根据短测随意改写点击调度。

- 显示刷新策略移入纯 Kotlin 的 ClockRefresh。普通时钟及距离触发超过 5 秒时每 100 ms 更新一次；已启用任务的最后 5 秒为 33 ms；隐藏数字时只保留 250 ms 生命周期检查。关闭浮层后取消更新。
- 点击截止仍由 OneShotRunner 的独立单调时钟回调处理，不依赖数字刷新回调决定触发。两者仍运行在主线程，系统或渲染阻塞造成的延迟没有被宣称消除。
- 一次准备任务只格式化一次固定目标时刻，倒计时继续更新；停止时清除显示缓存。
- 首页只在状态文字改变时更新 TextView；点位及目标时间在进入页面、选择时间和返回选位后更新，不每 500 ms 重新格式化并重设文字。

策略边界先写测试并运行 RED（ClockRefresh 尚未实现，编译失败），再实现 GREEN。新增 3 项测试，覆盖 5000/5001 ms、0/负值、极端 Long 值、隐藏优先与普通状态；总计 35 个单元测试通过。设备回归同时核对选择毫秒后按钮更新、返回首页后点位可见。

减少无效 invalidate/layout 与绘制阶段分配的原则参考 [Android 官方自定义 View 优化指南](https://developer.android.com/develop/ui/views/layout/custom-views/optimizing-view)。没有增加 DI、渲染框架、线程池或生产依赖。

## 同条件测量

两份 APK 都使用 R8/资源压缩、相同本地调试证书临时签名，确认无 DEBUGGABLE 标记。资源采样时没有附加 Instrumentation 或调试器。使用同一手机、相同前台独立测试页和时钟位置，预热后每 5 秒采样一次，共 9 次；每组实际约 47.5 秒。进程外读取 TOTAL PSS 与 /proc/PID/stat，CLK_TCK 为 100；CPU 表示一个核心的使用比例。

| 场景 | 优化前 CPU | 优化后 CPU | 优化前 PSS 中位数 | 优化后 PSS 中位数 |
| --- | --- | --- | --- | --- |
| 首页可见 | 7.443% | 0.927% | 79065 KiB | 71422 KiB |
| 测试页上的独立悬浮时钟 | 17.705% | 6.421% | 58206 KiB | 57266 KiB |

时钟 CPU 本次降低约 63.73%，PSS 中位数从约 56.84 MiB 到 55.92 MiB，本机常态目标达到。首页样本的内存波动较大（优化前 59675–87691 KiB），其 CPU 下降作为本次观察保留；不同前台场景的 PSS 差值不作为时钟增量开销。线程复测中 RenderThread 约 2.68%、主线程约 2.18%，与减少持续绘制工作的方向一致。

最后 5 秒仍采用约 30 Hz，常态低 CPU 数据不代表该阶段峰值。三位毫秒显示分辨率不等于显示每毫秒更新，也不代表 1 ms 真正点击精度。未签名 Release 从 158122 到 158346 字节，增加 224 字节。

## 点击和回归验证

- 优化后全部 12 组真机场景通过，包括实际录制与回放、准星、页面、定时单击、隐藏时钟和取消/停止。一次 Debug 样本派发晚 2 ms、目标 onClick 晚 50 ms，只收到一次；不把单次样本当成精度分布。
- 新增独立接收 APK 中的 ReleaseAcceptance，由公开界面设置 20 次 A/B 多点点击，实际收到 20 次且顺序一致。仪器化驱动附加在接收进程，不附加到 R8 应用进程。
- 配置两点等待为 100/300 ms；仓库脚本复验的 UP→下一次 DOWN 为 103–112/304–310 ms，达到次数后继续观察 700 ms，计数保持 20。完整事件保存在验收 JSON。
- 新入口 scripts/release-acceptance.ps1 会备份和恢复应用配置，临时签署优化包，结束后恢复 Debug；只重新连接本应用服务，保留其他服务列表。该脚本需要已开启 USB 调试安全设置和无障碍服务的真机，以及已启动过的 Debug 应用。
- 应用 Lint、Debug/Release 构建通过；辅助测试 APK Lint 为 0 错误、4 个测试包配置提示（旧目标 API、公开计数 Provider、备份配置和图标），不会打入正式应用。

重现优化包点击检查：

```powershell
$env:JAVA_HOME = '你的 JDK 17 目录'
.\scripts\release-acceptance.ps1 -Serial '真机序列号'
```

Gradle 缓存必须使用非 C 盘；脚本保持项目已有目录，拒绝 C 盘配置。离线依赖未准备时先按 README 完成常规构建。
